# 经验记录（Learnings）

## 2026-04-22

### 文档型 Apply 的验证方式要贴合产物类型

- 场景：本轮变更主要是 `devflow` 技能（DevFlow skill）与 references 文档更新，没有编译或测试入口
- 经验：不要为了“看起来像验证”去伪造构建或测试；更有效的验证证据是关键词落点搜索、正式 diff 检查与跨文档术语一致性核对
- 建议：后续类似技能文档优化任务，优先使用 `rg` + `git diff --check` + 人工通读一致性检查

### Markdown 结构调整时，整文件重写有时比局部补丁更稳

- 场景：`routing-and-stages.md` 在中途中断时出现了“删除后待恢复”的状态
- 经验：对于结构改动较大的 Markdown 文档，如果局部 patch 上下文不稳定，直接按批准设计整文件重写更能避免上下文错位
- 建议：先确认目标结构，再决定是局部 patch 还是整文件替换；中断后优先检查文件是否处于半成品状态

## 2026-07-04

### 原始需求不一定是单文件，需要索引化管理

- 场景：用户指出同一需求可能持续追加多个 prompt 文件，不能把 `origin.md` 设计成创建后不改
- 经验：原始输入（Raw Input）更适合用索引管理，记录相对路径、用途和吸收状态，而不是复制全文或冻结初稿
- 建议：后续 mission 初始化时创建 `origin.md`，但允许在新 prompt 出现时追加来源记录

### Apply 阶段的记录策略要避免打断实现节奏

- 场景：`优化思路-2.md` 明确指出 Apply 阶段频繁文档更新会打断实现节奏
- 经验：记录是主流程的一部分，但不同阶段的记录密度应不同；Apply 中只在回退、阻塞、暂停、上下文压缩或 Close 前写必要记录
- 建议：后续技能优化要区分恢复热路径（Resume Hot Path）与深度追溯路径（Deep Trace Path），避免把所有历史塞进 `state.md`
