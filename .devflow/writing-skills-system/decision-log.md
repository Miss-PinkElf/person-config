# 决策日志（Decision Log）

## 2026-07-07：建立写作技能体系 mission

- 决策：将本次工作记录到 `.devflow/writing-skills-system/`。
- 原因：用户明确要求使用 devflow 记录；需求涉及一组技能（skills）的设计与后续实施，适合长期 mission。
- 影响：后续需要遵循 Align -> Plan -> Spec/Tasks -> Apply -> Verify/Close 的阶段门禁。

## 2026-07-07：暂不直接创建单一总结技能

- 决策：先进行对齐（Align），不直接把原始提示词固化为一个技能。
- 原因：原始需求同时包含写文档、写文章、总结对话、提取知识点、知识延伸等多个使用场景，直接合并可能导致触发条件模糊。
- 影响：下一步需要确认技能拆分粒度与优先场景。

## 2026-07-07：第一版聚焦对话总结成知识文档

- 决策：第一版技能（skill）优先覆盖“对话总结成知识文档（conversation-to-knowledge-doc）”。
- 原因：该场景最贴近原始提示词，边界清晰，适合先验证输出结构与触发方式。
- 影响：本轮暂不默认覆盖已有材料写文章、长资料分段提取、全项目知识整理等更重场景。

## 2026-07-07：默认只使用当前对话与明确引用文件

- 决策：技能触发后，默认信息来源为“当前对话 + 用户明确引用的文件（explicit referenced files）”。
- 原因：避免自动扫描仓库造成背景污染，也能减少总结时引入未经确认的信息。
- 影响：如需读取仓库文件、devflow 记录或历史文档，需要用户明确引用或在后续版本中单独设计。

## 2026-07-07：输出结构倾向支持多模式

- 决策：第一版支持四种输出模式（output modes）：复盘型知识文档、教程型文章、项目沉淀文档、自适应结构。
- 原因：用户希望四种类型都覆盖；这些类型共享“对话总结成知识文档”的输入入口，但面向不同读者和沉淀目的。
- 影响：后续需要设计默认模式和切换规则，避免技能触发后反复追问或输出结构飘移。

## 2026-07-07：触发后先询问输出模式

- 决策：技能触发后，每次先询问用户选择输出模式（output mode）。
- 原因：用户明确选择“每次都先问用户选哪种”；不同模式的读者、结构和写作深度不同，由人先确认可以减少误写。
- 影响：技能流程需要在写文档前设置一个等待用户确认的步骤；除非用户在触发语中已经明确指定模式。

## 2026-07-07：文档默认输出到 zzz-docs

- 决策：生成文档默认统一输出到 `zzz-docs/`。
- 原因：这与原始提示词一致，路径简单稳定，不需要为第一版增加目录分流规则。
- 影响：技能需要在写入前确保 `zzz-docs/` 存在，并生成能体现主题内容的文件名。

## 2026-07-07：文件名采用主题 + 类型 + 日期

- 决策：生成文档文件名默认采用“主题 + 类型 + 日期”，例如 `写作技能体系-复盘型知识文档-2026-07-07.md`。
- 原因：用户明确要求日期放到后面；主题前置更利于人工浏览，日期后置仍保留时间信息。
- 影响：技能需要从对话中提炼主题和输出模式，并把日期附加到文件名末尾。

## 2026-07-07：知识延伸采用适度延伸

- 决策：知识延伸（knowledge extension）默认采用适度延伸。
- 原因：用户选择每篇文档 1-3 个自然关联点；这能保留“举一反三”的价值，同时避免文档膨胀成百科式罗列。
- 影响：技能需要根据当前主题选择强相关延伸方向，并说明为什么相关、有什么取舍（trade-off）。

## 2026-07-07：例子说明和取舍分析作为硬性要求

- 决策：所有输出模式都强制包含例子说明（examples）和取舍分析（trade-off analysis）。
- 原因：用户选择两个都强制；这也是原始提示词中最核心的写作质量要求。
- 影响：技能在生成文档前需要检查输出是否包含具体例子，以及“为什么这么做 / 为什么不这么做”的取舍说明。

## 2026-07-07：写文件前先展示大纲

- 决策：技能写入 `zzz-docs/` 前，每次先展示大纲（outline），用户确认后再写文件。
- 原因：用户选择“每次先给大纲，确认后再写文件”；这能提前校准结构、重点和延伸方向。
- 影响：技能流程需要包含大纲确认门禁；除非用户明确说“不要问，直接写”，否则不能直接落文件。

## 2026-07-07：第一版采用独立技能

- 决策：第一版做一个独立技能（independent skill），专门负责“对话总结成知识文档”。
- 原因：用户选择先做独立技能；该方式触发边界最清晰，也便于后续单独验证和迭代。
- 影响：暂不创建总写作技能（writing-docs）或复杂 references 体系；后续可在验证稳定后再抽象出写作技能套件。

## 2026-07-09：技能目录命名为 conversation-to-knowledge-doc

- 决策：第一版技能目录名使用 `conversation-to-knowledge-doc`。
- 原因：用户选择推荐命名；该名称准确表达“对话转知识文档”，比单纯总结更能覆盖知识延伸与文档化。
- 影响：后续计划和实施文档都以该技能名作为主标识。

## 2026-07-09：技能同时放入个人技能与仓库技能集合

- 决策：技能同时落到 `.codex/skills/conversation-to-knowledge-doc` 与 `skills/all-skills/conversation-to-knowledge-doc`。
- 原因：用户选择“两份都放”；这样既能被当前 Codex 直接发现，也能纳入仓库内技能集合管理。
- 影响：后续需要明确真相源（source of truth）和同步规则，避免两份内容演进不一致。

## 2026-07-09：仓库技能集合作为真相源

- 决策：`skills/all-skills/conversation-to-knowledge-doc` 作为真相源（source of truth），`.codex/skills/conversation-to-knowledge-doc` 作为同步副本。
- 原因：用户选择仓库内集中维护；这符合长期管理和版本追踪需求。
- 影响：后续实施时应先编辑 `skills/all-skills/...`，再同步到 `.codex/skills/...`，并验证两份内容一致。

## 2026-07-09：第一版采用主技能 + 模式参考文件

- 决策：第一版采用“主技能 + 模式参考文件（main skill + mode references）”方案。
- 原因：用户先选择单文件技能（single-file skill），随后明确改为方案 2；模式参考文件能让四种输出模式拥有独立规则，同时保持 `SKILL.md` 入口简洁。
- 影响：后续实施时应创建 `SKILL.md` 和 `references/` 下的四个模式说明文件；`SKILL.md` 负责触发、流程和路由，模式细节放入参考文件。
