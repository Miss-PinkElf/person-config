- bug-log / learning / docs
- 文档多了之后的索引的建立 / 还有滑动窗口来节省token

## 2026-04-30

### 思路

1. 是不是有些时候，还是预设提示词，而不是，skills，或者说是，需要先自己写一个workflow的 自定义命令，就是充当预设提示词，还好管理，怎么说
2. 怎么优化上下文，就是让devlfow的handoff，和下一个对话的提示短，精简
3. 感觉devflow的过程中是不是没有必要记录，是不是有浪费token，还是说再最后再通过命令进行收尾
4. 添加这个，就是devflow，需要标记一下，最新收尾时间，或者写下一个对话的提示词的时候，要有，或有一个json来标记，或者写一个vscode插件来管理

## 2026-05-08

### 思路

1. 能不能在创建mission的时候，就是自动创建一个skills或者cmd命令，自动指向，NEXT-SESSION-PROMPT-xxxxx.md
2. 或者多添加一个辅助的skills，让它可以辅助恢复上下文之类的，就是我发现每次都需要我手动恢复上下文
3. 对！，感觉自己的devflow缺少了一个需求的生命周期，或者是没有人来管理一个，开头结尾的生命周期
   1. 比如，恢复上下文，和对话的收尾
4. 一些说明文档，分析，不应该写到plan文件夹下面，或者这个可以作为一个rule补充到AGENTS.md里面

## 2026-05-09

### 思路

1. 生成的代码应该是可维护的，或者说有一定简单的注释，
2. spec文档应该是需要维护，或者是，用git记录版本？还是说package.json里面
3. 我感觉 devflow，要有一个基础的rule，或者说基础的编码原则，或者在初始化的时候，需要人提供基础rule，如果没有就用自己的，一些基础的rule，小而美的编码原则
4. 文档本身就变成了一个需要持续维护的工程产物：
   1. 代码改了，Spec 要不要同步更新？
   2. Spec 和实际代码不一致时，以谁为准？
   3. Spec 要不要版本管理？要不要 Review？
   4. 不同模块的 Spec 之间有依赖关系怎么办？
5. 感觉太多的文档，会影响，llm的注意力，devflow现在容易出现太多的文档，
   1. state，到后期可以会很长，是不是需要一个最新的state，还有一个历史的state，让llm专注于最新的state,或者有一个overview，概述一下，不要全量读取
   2. 是不是也可以有一个延期项/或者不确定后期需不需要做，文档或者文件夹，因为有些需求，不是一蹴而就的，是分步骤的，也会出现需求不明确的情况，以免后期遗忘
6. 有些时候一个大需求里面有小需求这个devflow或者说spec可以嵌套吗？
