# 核心思路与需求整理

## 一、插件定位

**受控第二文件管理器（Controlled Explorer）** — 在 VS Code 侧边栏新增一个独立的文件管理视图，里面的文件和文件夹由用户（或 AI）通过 JSON 配置精确控制，不与原生 Explorer 混淆。

### 为什么叫"受控"？

- 原生 Explorer 会显示项目中的所有文件和文件夹，信息量大且不可定制。
- 受控 Explorer 只展示用户**主动挑选**的文件和文件夹，入口清单集中在 JSON 配置中。
- JSON 配置天然适合 AI 维护，后续可通过 `controlled-explorer-config` skill 让 AI 自动管理。

---

## 二、核心需求演进（按时间线）

### 第一轮（prompt-1）：基础能力搭建

用户的核心诉求：

1. **独立的侧边栏入口**：在 Activity Bar 新增一个类似文件管理器的图标和面板，独立于原生 Explorer。
2. **自定义文件夹/文件清单**：只展示用户专门挑选的文件夹或文件。
3. **JSON 驱动配置**：用 JSON 管理入口清单，方便人工和 AI 共同维护。

### 第二轮（prompt-2）：交互增强与细节打磨

用户在第一版试用后提出：

1. **拖拽添加**：从编辑器标签页或原生 Explorer 把文件/文件夹直接拖到受控视图中。
2. **从配置移除（不删磁盘文件）**：在受控视图中删除入口时，只改 JSON，不删真实文件。
3. **文件改名同步问题**：配置文件中的路径指向的文件如果在磁盘上被改名，受控视图会报错/找不到 — 需要兜底。
4. **原生 Explorer 右键菜单**：在原生文件管理器的右键菜单增加"添加到受控文件"选项。
5. **排序能力**：
   - 默认排序：与 VS Code Explorer 一致（文件夹在前、文件在后，按名称排序）。
   - 频率排序：按文件在插件内的打开频率排序，高频文件靠前。

## 四、关键架构决策

### 4.1 方案选型：VS Code 扩展 vs 源码改造

- **决策**：第一版基于 VS Code 官方扩展 API 实现，不修改 VS Code 源码。
- **原因**：扩展 API（View Container、Tree View、FileSystem）已足够覆盖核心需求。源码改造会引入构建、分发、升级的巨大成本。
- **未来方向**：如果扩展 API 确认无法满足深层体验，再评估源码级改造。

### 4.2 JSON 配置结构

- **决策**：JSON 只记录"入口清单 + 虚拟分组"，不保存真实目录的 children。
- **原因**：真实目录的 children 从磁盘实时读取，避免 JSON 与磁盘状态不一致。

### 4.3 配置写入策略

- 添加入口 → 默认写入项目级 `.vscode/controlled-explorer.json#roots`。
- 移除入口 → 只改 JSON，不删磁盘文件。
- 默认排序 → 写入 JSON 时自动整理顺序。
- 频率排序 → 只影响视图展示，数据存入 `globalState`，不写回 JSON。

### 4.4 刷新策略

- 面板打开时读取配置。
- 手动刷新按钮。
- 监听配置文件变化 → 刷新根节点。
- 监听已展开目录变化 → 刷新对应目录。
- **不**全盘监听所有挂载目录（性能考虑）。

## 五、未完成任务 / 待观察

1. 未逐项执行完整手动验证清单（以用户实际使用反馈为准）。
2. TreeView 到终端的原生拖放体验可能受 VS Code 限制（已通过右键"发送路径到终端"兜底）。
3. 拖拽移动真实文件的稳定性需持续观察。
4. 没有自动化测试。
5. VSIX 产物被 `.gitignore` 忽略。
6. 外部拖拽 MIME 类型在不同 VS Code 版本可能不同。
7. 频率排序当前只统计受控树内打开行为，不统计原生 Explorer 或编辑器标签页。
8. `controlled-explorer-config` skill 目前只在 `.agents/skills`，未同步到 `.claude/skills` 或 `.codefuse/skills`。
